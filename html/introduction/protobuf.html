Protobuf encoding

Protocol Buffers turn a message into a compact sequence of bytes and back. Generated code hides the encoding. Knowing it helps when you read a captured frame, estimate the size of a directive, or write an encoder for a small microcontroller. The authoritative description is the Protocol Buffers guide Encoding.

Field numbers

A .proto file defines a message as a list of fields. Each field has a name, a type, and a field number:

message fldTstamp {
   fixed32 sec  = 1;
   fixed32 nsec = 2;
}

The wire carries field numbers, not names. A field number is never changed or reused, and a new field gets a new number.

Records

An encoded message is a sequence of records, one for each field that is present. A record is a tag followed by the value. The tag holds the field number and the wire type, which says how the value is stored:

tag = (field number << 3) | wire type

The wire type also tells a decoder how long the value is, so it can skip an unknown field. RCP clients use this for reports, but RCP servers reject unknown fields in directives, see Messages. The records can come in any order.

Numbers

Most numbers are varints: each byte carries seven bits of the number, least significant group first, and its most significant bit says whether another byte follows. The values up to 127 take one byte, the values up to 16383 two bytes, and so on. For example, 150 is written as 96 01:

150 in binary:                   1001 0110
in groups of seven bits:         0000001 0010110
least significant group first:   0010110 0000001
with the continuation bits:      10010110 00000001
                                 = 96 01

The types fixed32 and sfixed32 always take four bytes, least significant byte first. The schema uses fixed32 for the sequence numbers (msgDirective.seq) and for the fields of the timestamp (fldTstamp).

Length-delimited fields

Strings, bytes, and embedded messages are stored as a length, written as a varint, followed by that many bytes. An embedded message is a complete message of its own. A directive nests records several levels deep, from the operation to the action to the command of an endpoint. Each level adds a tag and a length.

Absent fields and defaults

A field that is not present takes no space. A singular scalar field without optional and outside a oneof does not track presence. An encoder omits its default value, i.e., 0, false, or empty. The receiver cannot distinguish an omitted field from an explicitly sent default. For example, an omitted msgDirective.seq has the value 0.

A field that is declared optional is different: the decoder can tell whether it was present, even when its value is 0 or false. The schema uses this for settings where “not set” means “leave as it is” and a value means “change it”, e.g., rcp.ptp.fldConfig.enable.

Message fields and oneof members also track presence. An empty fldAction.timed message still selects a timed trigger, and a selected oneof member with value 0 is still encoded.

A oneof selects at most one member. Standard protobuf decoders keep the last member if several appear on the wire. RCP servers instead reject such a directive before executing any operation, see Messages.

A repeated field stores a list, e.g., one record per operation in a directive. Repeated numbers are normally packed into a LEN record. An omitted list and an empty list have no distinct presence in the protobuf data model. Configuration-list updates follow the rules of esb.fldConfig.

Worked example

The directive that queries the identity of the RCP server is, in the text format:

seq: 1
dir { query { rcp: qryIdentity } }

Its encoded form takes 11 bytes: 0D 01 00 00 00 12 04 1A 02 10 0A.

01 00 00 00

The operation is 4 bytes long

The value 10, which is qryIdentity

The field fldQuery.hndl is 0, the RCP server itself, so it is not written. The maximum size of an encoded message depends on the frame type, see Network.
